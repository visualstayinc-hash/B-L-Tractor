## Bugs found and fixed during Pass 1 (with evidence)

1. **Mobile horizontal overflow (429px content in a 390px viewport).** First `verify.sh` run flagged this directly (`scrollWidth 429 > clientWidth 390`). Root cause, found by bisection: `.contact-direct` (the "studio@clearline.example — direct, no form required." line) contains the email as one unbroken token with no `overflow-wrap`, so in its narrow grid column (121px) it doesn't wrap and bleeds 67px past its own box — invisible to a per-element `getBoundingClientRect()` scan (zero elements reported `rect.right > innerWidth`) but real, and counted in `document.documentElement.scrollWidth`. Fixed with `overflow-wrap: break-word` on `.contact-direct`. Re-verified: `verify.sh` now reports "Overflow issues: none" at all four viewports.
2. **Six portfolio-plot SVG diagrams appeared blank in the first `verify.sh` run.** Investigated rather than assumed: a targeted script scrolled the page incrementally (real `mouse.wheel` calls) and confirmed every `.plotdraw` element ends at `stroke-dashoffset: 0px` — the diagrams draw correctly for a real user. The blank first screenshot was a **test-tooling artifact**: Playwright's `fullPage` screenshot can render below-the-fold content without physically scrolling the page, so the `IntersectionObserver`-gated draw-on animations never fired during that specific capture. Fixed by rewriting `scripts/verify.js` itself to perform real incremental `mouse.wheel` scrolling before every screenshot, so future evidence in this file is trustworthy rather than a false negative.

## Interaction evidence (terminal output, not screenshots — recorded here since QUALITY_GATE.md requires an evidence pointer)

- **Spine drag scrubs scroll live**: `scrollY` measured at 577 → 2309 → 4041 as the pointer moved across the spine mid-drag (real pointer simulation, not a click), confirming the drag is a continuous scrubber, not a discrete jump.
- **Spring-release overshoot is real, not just coded**: sampled `scrollY` every 40ms after release — rose to a peak of 2060, then eased back down to a final resting value of 2052 (i.e., overshot by 8px and settled back), matching the back-out easing in `springScrollTo()`.
- **Draw canvas registers real ink**: after a simulated pointer-drag gesture across `#drawCanvas`, `getImageData` confirmed non-zero alpha pixels were written.

## Bugs found and fixed during Pass 2 (interaction + motion review, with evidence)

3. **No persistent contact affordance (C04).** Content read-through found that contact was only reachable by scrolling/dragging all the way to the final section — a real client-trust gap, not just an untested row. Fixed by adding a "Start a line" link docked into the spine itself, visible from any scroll position, wired to the same `springScrollTo()` used everywhere else (not a plain instant anchor jump, to stay consistent with the one motion language). Verified: clicking it from the page-load position scrolled to and settled on `#contact`.
4. **`.crosshair` cursor class was dead code (S05).** CONCEPT.md promises "a fine crosshair with a live coordinate readout," but the CSS class existed and was never applied anywhere in the markup. Fixed by adding it to each `.plot__stage` along with a real `pointermove`-driven coordinate readout mapped to the SVG's own viewBox units — verified mathematically correct (center-of-stage hover produced exactly `"X 150 · Y 150"` for a 300-unit viewBox), not just visually present.
5. **Layout-thrashing read-after-write in `render()` (PF04, found during Pass 1's performance code-review, fixed here).** See QUALITY_GATE.md PF04 for the full detail — `offsetTop`/`offsetHeight` are now cached once in `buildTicks()` instead of being read after a same-frame DOM write on every scroll event.

Two test-script false negatives were also found and corrected **in the test scripts themselves**, not the site, during Pass 2 — recorded here for transparency since they could otherwise look like site bugs to a future reader: a `getComputedStyle(elementHandle, '::after')` call failed because Playwright's `page.evaluate(fn, arg)` doesn't marshal an `ElementHandle` into a raw DOM `Element` the way `getComputedStyle` requires (fixed by querying inside the evaluated function instead); and an hover-state check reported `false` for "visibly different" because the mouse was never moved away between two consecutive `.hover()` calls, so the "before" measurement was actually already-hovered (fixed by explicitly moving the mouse away first).

## Bugs found and fixed during Pass 3 (typography + image + portfolio review, with evidence)

6. **All six portfolio plots shared an identical layout (V02).** Each diagram is genuinely distinct, but the wrapper (text-left/diagram-right, same box size) was identical six times in a row, reading as monotonous under a fresh critical look — exactly the "repetitive section rhythm" the anti-slop checklist warns about, even though no single element was individually generic. Fixed with an alternating `.plot--rev` layout (plots 2/4/6 flip sides on desktop; on mobile the diagram appears before the text instead of after, confirmed via `getBoundingClientRect().top` comparison, not just assumed from the CSS).
7. **The alternation fix itself introduced a real overflow regression (caught immediately, not shipped).** `verify.sh` flagged `scrollWidth 420 > clientWidth 390` on mobile right after adding `.plot--rev`. Root cause: `.plot--rev .plot__grid` (two chained classes, specificity 0-2-0) overrode the mobile media query's single-column collapse `.plot__grid{grid-template-columns:1fr}` (specificity 0-1-0), since CSS specificity beats media-query source order. Fixed by adding an explicit `.plot--rev .plot__grid` override *inside* the mobile media query itself (matching specificity, later in source order, so it wins). Re-verified: `verify.sh` back to "Overflow issues: none."
8. **The core spine position math was wrong for 6 of 9 ticks (found while investigating an earlier "visual only" observation, turned out to be a real functional bug).** `section{position:relative}` is set globally (so plot diagrams' coordinate-readout `<span>` can be absolutely positioned within them), which meant `.plot-N`'s `offsetTop` was relative to `#work` (its nearest positioned ancestor), not the document — incomparable with the top-level sections' document-relative `offsetTop`. This silently corrupted the drag-to-nearest-tick snap target for every plot. Fixed by computing every section's position via `getBoundingClientRect().top + scrollY` instead of trusting `offsetTop` directly. Re-verified: a fresh drag-and-release landed within 0.48px of `plot-2`'s actual top (previously, this exact test would have snapped to a mathematically wrong position).

## Real contact info integration (scoped follow-up task, not a new pass — with evidence)

The placeholder `studio@clearline.example` was replaced everywhere with the real address `clear.line.studio.creative@gmail.com`, and real phone (`806-731-9998`, `tel:+18067319998`) and address (`3312 Ault Dr`) were added to the contact section's direct-contact block, tiered by visual weight (email primary, phone secondary, address tertiary, non-linked). The "Send" button's mailto link was also made to actually reflect the form's contents (subject/body built from whatever was typed) rather than opening a blank compose window — this isn't a fake backend, it's making an already-existing mailto link honestly use the data already on the page.

9. **A new overflow regression, caught before shipping.** Setting `align-self:flex-start` on `.contact-direct a` (to stop the underline decoration from stretching full-width) had the side effect of removing the width constraint that forces text to wrap — the flex item sized to its content's full width (max-content) instead of the 121px column, so the real (longer) email overflowed by 161px on mobile. `verify.sh` caught it immediately (`scrollWidth 522 > clientWidth 390`). Fixed by adding `max-width:100%` alongside `align-self:flex-start`, which keeps the shrink-to-fit sizing while still respecting the container's available width for wrapping. Re-verified: `scrollWidth` for the email link dropped from 282px (overflowing) to 121px (wrapped to exactly its column width), and `verify.sh` returned to "Overflow issues: none."
10. **A focus-indicator check gave a false negative, investigated and resolved as a test-methodology error, not a site bug.** `page.focus(selector)` (a programmatic DOM `.focus()` call) showed `outline-style: none` on the new email/phone links — but this is because Chromium's default focus-ring visibility is gated by `:focus-visible`, which a programmatic `.focus()` call does not reliably trigger, unlike a real keyboard Tab press. Redone with actual `page.keyboard.press('Tab')` navigation: both links correctly showed `outline-style: auto` (the same visible focus ring as every other link/button on the page) when reached by real keyboard navigation.

Regression check after this change (re-run, not assumed to still work): spine drag-scrub, the draw-canvas, the plot coordinate readout, and the spine's "Start a line" link were all re-tested end-to-end and confirmed still functioning exactly as before.

## Real email delivery (replacing mailto, with evidence)

The contact form's mailto-based "submission" (which just opened the visitor's own mail client) was removed entirely. The form now POSTs to Web3Forms, a no-backend form-delivery service, with a real loading → success/error UI cycle. Testing distinguished three genuinely different code paths, not just one happy-path check:

13. **Guarded "not configured" path** (current shipped state, placeholder access key in place): a valid, fully-filled form is intentionally blocked *before* any network call, showing "Delivery isn't configured yet" with phone/email fallback. Verified via a request listener that zero requests fire in this state — this isn't a guess, it's a measured absence of network activity.
14. **Honeypot path**: a bot-like submission (hidden field filled) is silently dropped client-side — verified zero network requests and no status-text change, so a bot gets no signal either way.
15. **Native-validation path**: an empty or malformed-email form is blocked by the browser's own `checkValidity()`/`reportValidity()` before my code runs at all — verified the same way (zero requests).
16. **The real network path — tested with a temporary key, reverted immediately, never committed.** To distinguish "the guard correctly blocks an unconfigured key" from "the actual fetch logic works," a non-placeholder test string was substituted for one test run only (`sed` on a single line, confirmed via `grep` before running, restored from a `/tmp` backup immediately after — never present in a committed state). This produced a genuine outbound `POST https://api.web3forms.com/submit`, confirmed via Playwright's request listener, which failed with `net::ERR_TUNNEL_CONNECTION_FAILED` — this sandbox's own network policy blocking the destination domain, the same restriction that has blocked every external domain this entire session (Google Fonts, the seven benchmark URLs, etc.). The loading state (button disabled, label "Sending…") and the `catch()`-driven error state (button re-enabled, fallback contact shown) both rendered correctly around that real failure.
17. **A new overflow bug, same root cause as bug #1, caught immediately.** The error-state message text (which embeds the full email address as one unbroken token) overflowed its 121px mobile column by 100px — `.contact-submit-cap` had never received the `overflow-wrap: break-word` fix that `.contact-direct` got back in bug #1, because it didn't exist as an error-carrying element until this task. Fixed identically. Re-verified: `scrollWidth` dropped from 490 to exactly 390 (the viewport width), and a full-page screenshot (`contact-form-error-state-mobile.png`) confirms the complete error message wraps cleanly across multiple lines with no horizontal scroll.

**What remains BLOCKED, not claimed as PASS**: actual delivery to `clear.line.studio.creative@gmail.com`. This requires a real Web3Forms access key, which only the inbox owner can obtain (Web3Forms ties the key to email verification of the destination address) — it cannot be fabricated, and this sandbox could not reach `api.web3forms.com` even with one. See `FINAL_REVIEW.md` for the exact setup step.

## Real key configured — conclusive root-cause finding (with evidence)

18. **The user supplied the real Web3Forms access key** (`c93a9106-98f4-4d02-b5fb-5e541e8ad9bf`, obtained via web3forms.com for `clear.line.studio.creative@gmail.com`). Configured in `index.html`, confirmed by direct `grep`, with the guard's comparison string deliberately left unchanged so the two strings now genuinely differ and the real fetch path executes rather than short-circuiting.
19. **A full real-key submission (desktop and mobile) was run and failed identically to the earlier placeholder-key test** — `net::ERR_TUNNEL_CONNECTION_FAILED`. This time the root cause was confirmed directly, not inferred: `curl -sS "$HTTPS_PROXY/__agentproxy/status"` (this session's own proxy diagnostic, documented in this environment's setup notes) shows a logged `"connect_rejected"` entry reading `"gateway answered 403 to CONNECT (policy denial or upstream failure)"` for `"host": "api.web3forms.com:443"`. This is a hard egress-policy rejection at this sandbox's own outbound gateway — the connection never reaches Web3Forms' servers at all, so no HTTP response, success or failure, was ever received from Web3Forms itself. This is not a code defect, not a bad key, and not fixable by further changes made from inside this sandbox.
20. **What this does not block**: this finding is specific to *this development sandbox's* network policy. The deployed artifact runs in a real visitor's browser, on their own network, which is not subject to this sandbox's proxy at all. That request path is untested from here by necessity — it requires a human opening the live URL and submitting a real test, then checking the actual inbox.
